## 1. Feature Context

- [ ] `p2` - `cpt-frontx-feature-routing-route-ownership-signal`

### 1.1 Overview

Route Ownership Signal publishes, rather than enforces, small independent facts derived from the URL at one domain, and orchestrates no mounting. It has three parts, all scoped to a single domain key at a time. First, **entry resolution**: given every entry the current location carries under one domain key and that domain's own set of registered extensions, it names, for each such entry, the route owner its extension token resolves to, or reports the entry as unresolved when no registration matches — a primitive every observer runs internally, not a public entry point of its own (DESIGN §3.2, Route Ownership Signal). Second, an **observer** the consumer creates once per domain — passing that domain's own registered-extensions source as a plain argument, never an injected port, together with that domain's own key: it subscribes to the navigation substrate's shared history and, on creation and on every subsequent navigation, reports one *transition* — the ordered list of entries currently carrying that domain key, resolved or unresolved, the cause of the change, and a diff against the previous report distinguishing entries added, removed, changed only in payload, or reordered — or no transition at all when the ordered list is unchanged, which is also what a navigation touching only a foreign domain key or the hash produces, since resolution reads only the entries carrying this domain's own key. Creating the observer also returns a release function the consumer calls to stop it. Third, a **URL back-projection helper** the consumer calls to write into the URL the extensions each command of the runtime names for a domain: it replaces that one domain's own entries with the caller's given delta — entries added (appended at the end of the full list), removed (leaving no gap), changed only in payload (in place, at their existing position), replaced (an existing entry's own extension token swapped for a new entry at that same position), or reordered (this domain's own entries taking a new relative order within the set of positions they already occupy) — removes, in that same single history write, every entry under each domain key the delta's `clearedDomainKeys` names (structural reset: the exact nested routed domains the caller knows leave with an extension the delta removes or replaces), and copies everything else — including every entry under the same domain key that the delta does not name — verbatim. The helper infers no domain key to clear from any key's shape or from a lexical prefix: a domain key is the domain's own declared route, a single `name` carrying no ancestry (`cpt-frontx-routing-adr-domain-occupancy-addressing-granularity`), so which domains nest in a departing extension's zone is a fact only the caller holds. None of the three touches mounting, unmounting, a registry of route owners, or a state machine tracking which owner currently occupies a domain — those facts and that occupancy belong entirely to the `mfes` runtime, which the FrontX router reaches only through `mount_ext` and `unmount_ext` actions.

Resolving a URL several domains deep is a wave through the tree of domains, not one event: each domain's own observer resolves and reports independently the moment that domain comes to exist, reading whatever the shared history's `location` already is at that moment, never a value captured earlier. That is the observer; the FrontX router's substitution of the initial route for a domain that starts during a page load is separate from it (§1.4, Binding obligation, point 9). The signal holds no registry of domains and publishes no signal asserting that a whole address resolved end to end — it cannot, by construction, since the signal never sees the tree of domains. The FrontX router's own copy of the registrations is stated in the Boundary note (§1.4). A domain resolving to no entries at all is, for exactly this reason, indistinguishable from "the wave has not reached this domain yet" until that domain's own observer comes to exist and reports.

In a composed application the consumer of the observer and of the back-projection helper, for every routed domain, is the FrontX router (`cpt-frontx-routing-actor-frontx-router`): the router this package provides, which conforms to the runtime's abstract router (`cpt-frontx-adr-extension-routing-port`, `cpt-frontx-component-routing-router`). Throughout this FEATURE, *the consumer* names it. An occupant's own engine provider also calls the back-projection helper, to write that occupant's own entry's own parameters as a payload change (`cpt-frontx-feature-routing-engine-provider`); it never names an addition, a removal, a replacement, a reorder, or a domain key to clear.

### 1.2 Purpose

A composed application's routable domains must resolve the same way regardless of how the user arrived at a URL — typing it, reloading it, stepping back or forward through history, or following a link — and that must hold at every domain a composed application actually nests, not only at the outermost one, and at every occupant count a domain's own occupancy strategy admits, not only a single occupant. But the runtime that actually owns domain occupancy — named mount strategies, a cardinality matrix, and a registry of what is currently mounted — is the `mfes` runtime, not this library, and it changes occupancy only by executing `mount_ext` and `unmount_ext` actions; the full boundary this draws is owned by `cpt-frontx-routing-principle-publishes-not-orchestrates` (DESIGN §2.1), not repeated here. Route Ownership Signal exists to give the FrontX router — the party that, for every routed domain, admits the domain's and its extensions' registrations, starts and stops the domain's observer, assigns each mounting extension its occupant value, turns a user's change to the URL into actions chains, and writes into the URL what the runtime commands (`cpt-frontx-adr-extension-routing-port`, Commanding the URL, URL ownership) — the URL-derived facts it turns into actions chains, and the one write path through which it writes each command into the URL, at whatever depth and whatever occupant count a domain has, without this package ever holding, orchestrating, or guessing at that occupancy itself.

**Requirements**: `cpt-frontx-routing-fr-route-ownership-signal`, `cpt-frontx-routing-fr-concurrent-occupant-projection`, `cpt-frontx-routing-fr-per-occupant-addressable-parameters`, `cpt-frontx-routing-fr-frontx-router`

**Boundary note**: The signal, the entry-resolution primitive, the observer and the back-projection helper hold no registry of route owners. The FrontX router keeps its own copy of the registrations, in ids, routes and one boolean per domain, and uses the nested-domain record in the realm-shared router state (Binding obligation, point 3); the authoritative registry of route owners stays with the runtime. Nothing in this feature executes a mount or unmount, at any domain, or carries an occupancy model of its own — the full boundary is owned by `cpt-frontx-routing-principle-publishes-not-orchestrates` (DESIGN §2.1), not repeated here. The signal's coupling to the FrontX router, and through it to the runtime that executes mounts, is expressed only through the plain-argument registered-extensions source, the observable signal's transitions, and the back-projection helper's input, per domain — never through an injected port and never through an import of the runtime that owns occupancy or of the FrontX router.

**Registry grounding**: The registered-extensions source the FrontX router supplies for a domain (§1.5) has a natural origin this feature does not decree: the runtime's own registry of route-owner declarations. A route owner's own extension token is that declaration's own normalized route-identity value — which concrete field on a registration supplies it is the `mfes` package's own contract (`cpt-frontx-routing-adr-occupant-identity-stability`) — the derivation itself is the navigation substrate's own name-validity primitive (`cpt-frontx-algo-routing-navigation-substrate-name-validity`, Extension-token derivation), not redefined here. Uniqueness of a declared extension token among a domain's own registrations is the FrontX router's registration-time check (PRD §11; DESIGN §2.3, O3b). Which route a domain declares, at any depth, is likewise not decided by this feature: it is the domain's own declared route, admitted by the FrontX router only when no other routed domain live in the page already holds it (DESIGN §2.3, O1) — this feature only resolves against whatever domain key it was handed, never against how that route was chosen. That every child microfrontend runs its own registry, unreachable by enumeration from its own parent, is what makes a per-domain registered-extensions source a structural necessity rather than a convenience — no single registry could enumerate every domain's own occupants even if this feature wanted one to.

**Binding obligation**: Turning a user's change to the URL into actions chains, and writing into the URL what the runtime commands, is not this package's obligation on its own, at any domain — it is the FrontX router's, built on this signal and this helper (PRD §11; `cpt-frontx-adr-extension-routing-port`, Commanding the URL, URL ownership). This feature is the single normative statement of the FrontX router's behaviour behind DESIGN §2.3's obligations O1, O3a, O3b, O5, O6 and O7: admission is specified by §3 (Router Admission And Lifecycle), and the rest by the flow of §2 and the algorithms of §3; DESIGN §2.3 states those obligations only with a pointer here. Points 1–11 below are informative: a summary of §2, §3 and §5, whose flows, algorithms and Definitions of Done are normative. The obligation is recursive: the FrontX router carries it for every routed domain, with no lesser or different obligation for a domain several levels deep than for the outermost one, and no lesser or different obligation for a domain admitting several concurrent occupants than for one admitting a single occupant. For every routed domain, the FrontX router:
1. Creates the observer described in §3 (Observable Transition Signal) for that domain once the runtime reports that the domain's root has attached (`startDomain`), its route having been admitted at registration (§3, Router Admission And Lifecycle), supplying that domain's own registered-extensions source and the domain's own declared route as its domain key.
2. On each notified transition whose cause is `initial` or `history`, turns the changes the transition's diff reports in that domain's entries into `mount_ext` and `unmount_ext` actions chains sent through the actions-chain executor the runtime hands it (DESIGN §2.3, O6). The cause `initial` covers a page load — a cold load, a reload, or an address the user enters — including each domain's first resolution and a nested domain whose observer starts when its host mounts, in the breadth-first load of the domain tree; the cause `history` covers a back or forward step. For such a transition the FrontX router sends one `unmount_ext` for each token the diff reports removed, only when the domain declares `unmount_ext`, and one `mount_ext` of the named route owner for each token the diff reports added that resolves (an unresolved entry sends no mount, step 6). Each is its own actions chain, carries the history intent `none`, because the URL already says what the mounts must become, and has no `fallback`, and nobody waits on it; removals are dispatched before additions, in dispatch order, and a removal's failure holds back no addition. A transition whose cause is `push` or `replace` dispatches nothing (point 4). The FrontX router never reads what is mounted to decide what to dispatch: the domain's handler decides the outcome of every request, including a request for an already-mounted or already-absent extension and a request that overlaps a mount or unmount of the same extension in flight. An entry the diff reports changed only in payload needs no chain: the already-mounted occupant's own router reads its updated payload from the shared history. Reordering alone implies no chain of its own. The FrontX router never mounts, unmounts, or reconciles directly off a transition. This feature resolves no mount race of its own — a chain driven by this signal races against, and is resolved by, exactly the same runtime mechanism any other chain already is.
3. Writes into the URL, through the URL back-projection helper (§3, URL Back-Projection Helper Via Own-Key Rewrite), exactly the extensions each command of the runtime names for that domain, with the command's verb (point 6; DESIGN §2.3, O5). It expresses the command, in one helper call, through the back-projection helper's write operations (§1.5, URL back-projection — input): when, for that domain, the command drops exactly one extension and names exactly one new one, the new one takes the dropped one's position as a `replaced` operation; otherwise the dropped extensions are `removed` and the new ones are `added` at the end, in the command's order; a dropped extension is one present in the domain's live entries that the command does not name, a new one is one the command names that is not present; entries the command keeps are left unnamed in every case, so they keep their position and their parameters. When a command drops an extension whose zone hosts routed domains, the call's delta names, in `clearedDomainKeys`, every domain key nested beneath that extension, transitively, so their entries leave in that same single write (DESIGN §2.3, O7). The FrontX router takes these keys from the nested-domain record in the realm-shared router state. When a runtime is itself an extension, its FrontX router records there, under that runtime's own occupant value, the key of each routed domain it registers, and removes the key when the domain is released; when its navigation is supplied after a domain registered, it records that domain's key at that point (§3, Router Admission And Lifecycle, steps 2, 4 and 9). For each dropped extension, the FrontX router collects the keys recorded under that extension's occupant value — the domain's key and the extension's name. Then, for each collected key, it also collects the keys recorded under every occupant value whose domain key is that key, to any depth, so the nested domains of a nested host leave too. The nested releases inside the departing host's own execution issue no command and write nothing of their own. A command whose result equals the live URL writes nothing, and makes no helper call, since the helper itself writes on every call (§3, No-op note). A command for a domain whose enclosing entry is absent from the URL is deferred while that entry is absent and issued once that entry is present; the enclosing entry of a nested domain is the URL entry of the extension that hosts that domain. While a domain's write is deferred, a later command for that domain takes the place of the pending one, so a single deferred write remains; its verb is `replace` if any of the commands it combines carried `replace`, otherwise `push`, and it is composed and compared against the live URL when it is issued, so an equal result writes nothing. A back or forward step by the user before the enclosing entry is present cancels every pending deferred write before any observer dispatches for that step, so a write-back the step itself defers is kept; an extension released while the write is deferred is dropped from it. A command for a domain without a live observer writes nothing. Unregistering an extension or a domain, and terminal disposal of a registry, are resource cleanup, not actions: they issue no command and produce no helper call, and an entry they leave behind stays unresolved or inert (`cpt-frontx-adr-extension-routing-port`, Unregistration and disposal).
4. Dispatches nothing for the transition its own write produces (DESIGN §2.3, O6): the helper's own history call is a written navigation, so the navigation substrate's fan-out (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`) delivers it with the kind `push` or `replace`, the observer reports it with that cause, and point 2 dispatches only for `initial` and `history`. The same holds for a programmatic navigation and a navigation through the navigation facade, an extension's or the shell's, which are written navigations too.
5. Does not wait for a transition to conclude a domain has no occupant. Creating the observer against a domain key no entry currently carries reports an initial transition with an empty entry list and an empty diff (§3, Observable Transition Signal) — not the absence of a report — so a FrontX router that treats an empty entry list as "no occupant" from the moment it creates the observer needs no separate signal for that state.
6. Passes, as the helper's verb, the verb of the command it writes: the application request's own `push` or `replace` for a command the runtime issues when the domain accepts that request, and `replace` for a command the runtime issues when a request settles; its own write after a user's change (point 9) is a `replace` (DESIGN §2.3, O5, O6). Every chain of point 2 carries the history intent `none`, which issues no command at acceptance, so its settle command, a `replace`, never creates a history entry. The helper accepts the verb as an explicit argument rather than fixing it itself (§3). The open-with-`push`, close-with-`replace` asymmetry — opening with `push` so a back step closes what was just opened, closing with `replace` so a back step after closing does not resurrect what was just dismissed, and a switch (the delta's `replaced` operation) opening with `push` so a back step returns to the entry it replaced — is the convention whichever party sends the request expresses through that request's own history intent (DESIGN §4, "A back-projection write and its chosen history verb"); the helper does not enforce it.
7. Applies the "same domain, same entries → no transition" rule within its own domain key only: a change to an entry under a foreign domain key, or to the hash, is not itself a transition, because resolution reads only the entries carrying this domain's own key.
8. Leaves a parent without rewriting the history entry the user is leaving. Because point 3 clears a departing host's nested domains in the same single write as the command that drops the host, no write ever strips the nested entries from the entry being left — neither before that command's write nor after it. Under `push` — the verb of an accepted opening or switching request — that entry survives intact in history, carrying the host's own entry and every nested occupant's own entry with that occupant's own parameters. A Back step lands on it, and a Forward step on the state after leaving; each is a `history` transition, so point 2 brings the mounts to it — the host together with its nested occupants, each reading its own entry's own parameters — through chains carrying `none`, which issue no command at acceptance and whose settle commands equal the URL and write nothing. This is the FrontX router's behaviour; what this package guarantees toward it is the helper's own: exactly one history write per call, clearing exactly the domain keys the call supplies (§3, URL Back-Projection Helper Via Own-Key Rewrite, Single-write note).
9. After dispatching the chains of a transition whose cause is `initial` or `history`, writes the URL with `replace`, so the write never creates a history entry (flow step 8; DESIGN §2.3, O6). A page load sends its chains from the initial route, and the FrontX router then clears the URL's entries exactly once per page load: synchronously, right after dispatching the chains of the load's first `initial` transition, it clears every entry from the URL, leaving everything else in the URL as it is, and it clears even if a send throws; a settle command runs in a later turn, so no settle write precedes the clear, and no later `initial` transition clears; from then on the URL carries only the entries the runtime's commands write, so an entry no chain mounts — an extension token no registration matches, a domain key no domain on the page reads, a mount that fails — is absent from the URL after the load. It keeps the initial route for two uses only: every domain, root or nested, whose observer starts while the FrontX router keeps the initial route takes its first resolution from it, not the cleared URL; and the first write of an extension the initial route named carries its entry's parameters as the initial route carried them. The cleared URL carries no entry for such an extension until that first write puts it back, so the extension sees its own subroute only from that write on, and a deep link into an extension's own subroute survives the load only through that first write. It discards the initial route at the first acceptance command it receives, recognized by the verb `push`, which only an acceptance command carries (its own chains carry `none`, and every settle command is a `replace`), or at the next back or forward step, whichever comes first (flow step 9). A back or forward step first cancels every pending deferred write (point 3), so the write-back below is composed for the step alone. The kept initial route and the once-per-load clear are one per page, shared by every FrontX router copy in the page, since a nested host's runtime has its own copy. For a back or forward step, it writes that domain's entries, composed and written as point 3 writes a command, so a result equal to the live URL writes nothing: entries that do not resolve are dropped; and for a domain that does not declare `unmount_ext` whose entries the change left empty once those are dropped, the extensions of the last command it received for that domain are written back, because no request reaches the runtime for that change and the runtime has nothing to command. An entry that does not resolve is logged only for a transition after the domain's first one, never for the URL as found when the domain's observer starts. Raw user input, typed or bookmarked, that carries two tokens in an Exclusive or Optional domain shows both until the first settle command for that domain (`cpt-frontx-adr-extension-routing-port`, Consequences).
10. Keeps, per domain, only the extensions of the last command it received, used solely for the write-back of point 9; it drops an extension from that record, and from any deferred write of point 3, when the extension is released, and drops the record, together with that deferred write, when the domain stops; a back or forward step cancels the deferred write (point 3) (DESIGN §2.3, O6; `cpt-frontx-adr-extension-routing-port`, URL ownership). Until it discards it (point 9), it also keeps a page load's initial route, used solely for the first resolutions and the first writes of point 9. It holds no picture of what is mounted and reads neither an action's type nor its outcome.
11. Reads one fact about a domain's declaration: whether it declares `unmount_ext`. It reads nothing about the domain's strategy, cardinality, or queue (DESIGN §2.3, O5).

Further obligations apply once more than one domain, or more than one occupant per domain, is in play:
- A domain key with no observer currently reading it is inert — not an error, not a fallback state, and indistinguishable from a domain whose own wave has not yet reached it. Because point 3 clears the entries of a departing host's nested domains in the write of the command that drops the host, and point 9 clears every entry a page load carries once its chains are sent, an inert entry is one neither of them removed — an entry a back or forward step brings back, or one unregistration or disposal left behind; an entry that does survive resolves correctly the moment a domain that reads it comes to exist, because every observer always reads the URL's current, live state, never a value captured earlier. During a page load, a domain, root or nested, whose observer starts while the initial route is kept takes its first resolution from the initial route the FrontX router kept (point 9).
- Several domains wave independently: one domain's own transition and a sibling or nested domain's own transition carry no ordering guarantee relative to each other; when the FrontX router needs one to wait for the other, it coordinates that itself.
- Teardown of the occupant whose zone contains a nested domain — part of the parent action's own execution — releases that nested domain's observer, through the FrontX router, nested first, outermost last, or in whatever order the FrontX router already tears down the zone's own contents. An observer left running past its own zone's teardown continues resolving and reporting against a domain key and a registered-extensions source whose owning zone no longer exists, reporting to a FrontX router that itself no longer has anything meaningful to do with the report.

Without the FrontX router carrying this obligation at every routed domain, the primitive, the signal, and the helper this feature publishes describe facts, not a URL that follows the application — dispatching a user's change to the URL and writing the runtime's commands is the FrontX router's obligation, built on this package's surfaces, not this package's alone.

**Multiplicity note**: More than one observer may exist in the same realm at once — one per routed domain, never more, regardless of how many occupants that domain's own occupancy strategy admits at once (`cpt-frontx-routing-fr-concurrent-occupant-projection`). A domain holding several concurrent occupants is resolved, observed, and back-projected by the identical one observer and one helper any domain uses; concurrency is a property of how many entries that domain's own ordered list carries, never a reason for a second observer. Each observer is independent, is created with its own registered-extensions source and its own domain key, tracks its own previously reported ordered entry list (§3, Observable Transition Signal), and is released independently (§3, Observer Release). All of them read the one navigation substrate's shared history and fan-out (`cpt-frontx-routing-principle-single-history-authority`), so every observer resolves against the same `location` a given round dispatches, but resolves it against its own domain's own registered extensions and its own domain key's own entries — which is exactly what makes resolving a deep URL a wave rather than one event (§1.1).

### 1.5 Contract Shapes

Field-level shapes for this feature's own inputs and outputs, per `cpt-frontx-adr-contract-schema-ownership` (owned contract role in DESIGN, decision rationale in the ADR, field-level schema in the owning FEATURE).

**Construction seam**: the observer (§3, Observable Transition Signal) and the URL back-projection helper (§3, URL Back-Projection Helper Via Own-Key Rewrite) are both obtained from a single factory bound to one navigation substrate `NavigationHistory` instance at once — never resolved by either one internally, and never defaulting silently to the realm-shared singleton behind a caller's back. Both read and write exclusively through the identical instance the factory was given, so a consumer testing against its own instance, or an SSR entry point supplying its own, gets the same read/write consistency an ordinary consumer bound to the realm-shared singleton gets. §3's own algorithm descriptions below state each half's behaviour against "the navigation substrate's shared history" generically; which concrete instance that is, is exactly what this factory's own binding fixes for both halves at once (DESIGN §3.3, `createRouteSignal`).

**Registered-extensions source** (supplied per domain by the FrontX router, passed as a plain argument — never an injected port):
- The set of registered extension tokens for that one domain, which the observer reads afresh at each resolution, the initial one and the one of every later navigation, in the same shape this feature's entry-resolution primitive reads; no extension token appears twice (PRD §11; DESIGN §2.3, O3b). An extension registered after its domain started is resolvable from the next navigation on, and one released resolves as unresolved from then on; the observer does not watch the set, so a change to it causes no resolution of its own. Known limit: the URL's entries are cleared after the page load's first transition, and the initial route stays captured until the first `push` command or back/forward step; a deep link is lost only for an extension whose registration is not in place when its domain's observer takes its first resolution.
- Declares no cardinality floor: zero registered extensions is legal and simply means every entry under that domain key resolves to unresolved.

**Transition** (this feature's own output, delivered to the callback the consumer registers when creating one domain's own observer; never delivered at all when nothing about the ordered entry list changed, except the initial transition at observer creation, which is always delivered, including with an empty entry list):
- The domain key this transition concerns.
- **Cause**: why the entries changed — `initial` for each domain's first resolution when its observer starts: a cold load, a reload, and an address the user enters are page loads and arrive as `initial`, and so does the first resolution of a nested domain whose observer starts when its host mounts, as part of the breadth-first load of the domain tree; every `initial` transition dispatches. For a transition produced by a history-layer notification, the navigation kind that notification carries: `history` for a navigation delivered through the browser's own subscription (a back or forward step, a `go`, a third-party `history.go`, a fragment-only change), `push` or `replace` for a navigation written through the history layer (the FrontX router's own back-projection write, a programmatic navigation, a navigation through the navigation facade, an extension's or the shell's). A fragment-only change touches no domain entry, so it changes no transition.
- **Entries**: the ordered list of every entry the current location carries under this domain key, in the order the grammar codec's own parse preserves — each carrying its own extension token and its own ordered payload params, and each flagged either resolved (a registered extension matches) or unresolved (none does).
- **Diff**, against the previously reported ordered list:
  - *Added* — extension tokens present now that were absent from the previous report.
  - *Removed* — extension tokens present in the previous report that are absent now.
  - *Payload-changed* — extension tokens present in both reports whose ordered payload params differ between them, with the extension token itself unchanged; a payload-only change never appears in *Added*, *Removed*, or as a cause of *Reordered* on its own (`cpt-frontx-feature-routing-navigation-substrate` §1.5, URL grammar; DESIGN §1.1, Structural reset).
  - *Reordered* — whether the relative order of the extension tokens present in both reports changed, independent of whether any of them also carries a payload change.
  - *Unresolved* — the subset of Entries currently flagged unresolved, listed here so a consumer need not scan Entries to find them; not itself a diff category against the previous report, only a restated subset of the current Entries.
  - A `replaced` back-projection write (§3, URL Back-Projection Helper) is not itself a further diff category: it is observed exactly as the old extension token appearing under *Removed* and the new extension token appearing under *Added*, both at the position the write assigned them — the diff stays agnostic to which back-projection operation produced the change it reports.
- No transition is delivered at all — not a further field value, an absence of delivery — when every one of the four diff categories above (*Added*, *Removed*, *Payload-changed*, *Reordered*) is empty or false relative to the previous report, regardless of whether the current Entries list itself is empty or non-empty, except the initial transition at observer creation, which is always delivered, including with an empty entry list; this is what a navigation that changes only a foreign domain key's own entries, or the hash, produces, since resolution reads only the entries carrying this domain's own key.

**Router members** (the router-side behaviour of each member of the runtime's abstract router; the members and their signatures are owned by `cpt-frontx-dod-mfe-host-communication-router-port-contract`, in `cpt-frontx-feature-mfe-host-communication`, and no input names a runtime type):
- `connect` — called once, before any domain or extension registers. The router keeps the executor and the type system it is handed, as its own abstract dependencies (below), and uses them only to send the chains of point 2.
- `registerDomain` — a throw rejects the registration; when the router's own runtime is itself an extension, the router records the domain's key in the nested-domain record, under the runtime's own occupant value (§3, Router Admission And Lifecycle; DESIGN §2.3, O1, O7).
- `registerExtension` — ignored for a domain the router did not admit as routed; a throw rejects the registration (§3, Router Admission And Lifecycle; DESIGN §2.3, O3a, O3b).
- `releaseDomain` and `releaseExtension` — free what the router admitted: a released domain's route, its key in the nested-domain record, its observer and any deferred write; a released extension's name, and its place in the domain's last-command record and in any deferred write (point 10).
- `startDomain` — starts the domain's observer once the domain's root has attached; a second call reuses the running observer. `stopDomain` — stops it before the domain detaches, and drops the domain's last-command record and any deferred write (point 10).
- `reflect` — the runtime's command: the ordered list of extensions the domain must show, and the verb, `push` or `replace` (point 3).
- `assignOccupantValue` — returns the extension's occupant value, `{ domainKey, extension }`: the domain's route and the extension's name, with no ancestor; returns `undefined` for an extension or domain the router did not admit as routed. The runtime stores the value without reading it.
- `supplyNavigation` — the router records that navigation was supplied, keeps the reader of the runtime's own occupant value it is handed, and records every domain it has already admitted under that occupant value in the nested-domain record, removing any record of those domains under a previous occupant value.

**Router's abstract dependencies** (this package's own types, which the executor and the type system handed to `connect` satisfy structurally): `ActionsChainExecutor`, whose one member, `executeActionsChain`, takes a chain and returns nothing; and `RouterTypeSystem`, whose two members, `resolveMountExtActionId` and `resolveUnmountExtActionId`, each return an action type id.

**Engine-provider read** (not a member of the runtime's abstract router): `ownEntryAddress()`, read by the engine-provider package, has three cases. In a routed extension's runtime, it returns the runtime's own occupant value once validated, `{ domainKey, extension }`. In the shell runtime, the runtime whose router was never supplied navigation (`supplyNavigation` is called only in an extension's runtime), it returns `undefined`; there, the engine-provider package's extension router and navigation facade work over the shell's subroute (the pathname) only. In an extension runtime whose router was supplied navigation but has no occupant value (an extension with no route of its own or of its domain, or a failed occupant-value exchange), it throws: that extension has no access to the router, so its extension router and `navigation()` refuse too. The FrontX router itself never calls this read: it records its nested domains under the occupant value it holds internally (§3, Router Admission And Lifecycle, steps 2 and 9). An extension must build its registry within its mount window: an extension runtime that builds no registry, or builds it outside the mount window, never adopts its inbound bridge and is never supplied navigation, which is a defect of the MFE entry and lies outside the private-subroute guarantee.

**Chain the FrontX router sends** (point 2): `{ action: { type, target, payload: { subject, history: 'none' } } }`, where `type` is `resolveUnmountExtActionId()` or `resolveMountExtActionId()`, `target` is the domain's id and `subject` is the extension's id; it carries no `next` and no `fallback`.

**Release function** (this feature's own output, returned to the consumer at observer creation, alongside registering its callback): a zero-argument function that, when called, unsubscribes the observer from the navigation substrate's fan-out (§3, Observer Release). Calling it more than once is a no-op after the first call.

**URL back-projection — input**: the domain key whose own entries the caller wants written; a delta describing what changed, naming five kinds of change to this domain key's own entries, each keyed by extension token: an ordered list of entries to **add** (appended at the end of the full list); a list of extension tokens to **remove** (no gap left); a list of `{extension, params}` pairs whose payload changed **in place**, with the extension token itself unchanged — `params` is the entry's entire new ordered parameter list, replacing the one it already carries rather than merging into it; a caller wishing to keep a parameter that entry already had passes it again; a list of `{oldExtension, entry: {extension, params}}` pairs each **replacing** an existing entry's own extension token with a new entry at that same position; and, optionally, a **reordered** relative order for this domain's own currently-present entries, applied only within the set of positions those entries already occupy, leaving every other domain's own entries untouched. Alongside those five, the delta carries **`clearedDomainKeys`** — a list of domain keys naming exactly the nested routed domains the caller knows leave with an extension the delta removes or replaces; every entry under each named key is removed in the same history write as the rest of the delta (structural reset). The helper infers no domain key to clear from any key's shape or from a lexical prefix, and does not check that a named key belongs to the zone of a removed or replaced extension — it holds no record of which domains nest where (DESIGN §3.2, Route Ownership Signal, Responsibility boundaries). Together with the history verb the caller chooses, `push` or `replace` (§1.4, Binding obligation, point 6). The caller names only what changed; every entry under this domain key the delta does not name, and every entry under every other domain key `clearedDomainKeys` does not name, is left to the helper's own verbatim copy.

**URL back-projection — output**: one `push` or `replace` call, whichever verb the caller chose, against the shared history, that: writes this domain key's own ordered entry list with the delta's additions appended, the delta's removed extension tokens absent, the delta's payload changes applied in place at their existing position, each replaced extension token swapped for its new entry at that same position, and this domain's own entries reordered as given — within the positions they already occupied — when the delta names a reorder; removes every entry under each domain key `clearedDomainKeys` names — other than this domain key itself, whose own entries the delta alone governs — and no other entry; and copies every entry this domain key's own delta does not name, and every entry under any other domain key `clearedDomainKeys` does not name, verbatim in structure — the Escape-canonicalization note in §3 says what "verbatim" does and does not cover for an entry's own percent escapes. The helper reports nothing back to the caller beyond letting the underlying `push`/`replace` call either succeed or throw whatever the shared history itself throws, or throwing on its own for an input it rejects (§3, the validation of step 1.1, the replaced-presence check, the reorder permutation check, and the Collision note).

      1. [x] - `p1` - Pair the entry with "unresolved" - `inst-pair-unresolved`
3. [x] - `p1` - **RETURN** the ordered list of `{entry, resolution}` pairs - `inst-return-resolution`

**Rationale**: This algorithm is a thin filter-and-match over the substrate's own grammar codec and name-equality predicate, called once per domain; it defines no parsing or matching rule of its own, so a change to either — the codec's own parse rules, or the name-equality comparison — is a change to the navigation substrate's own algorithms alone (`cpt-frontx-feature-routing-navigation-substrate` §3), never to this one. Resolving to "unresolved" rather than dropping an unmatched entry is what lets a domain's own consumer report it; it leaves the URL when the FrontX router clears the URL's entries once a page load's chains are sent, or is dropped by the FrontX router after a back/forward dispatch, and an extension registered later resolves from the next navigation (§1.1; DESIGN §1.1, Structural reset).

### Observable Transition Signal

- [x] `p2` - **ID**: `cpt-frontx-algo-routing-route-ownership-signal-observe-change`

**Input**: A domain's own registered-extensions source, passed as a plain argument at creation (never an injected port); that domain's own key — its declared route, a single `name` — passed at that same moment; a callback the consumer registers to receive a transition; the navigation substrate's shared history and its fan-out subscription; the observer's own internally tracked previously reported ordered entry list, updated after every resolution this algorithm performs.

**Output**: An observer subscribed to the navigation substrate's fan-out, plus a release function returned to the consumer at creation (`cpt-frontx-algo-routing-route-ownership-signal-release`); on creation, and on every subsequent navigation that changes something about this domain key's own entries, one call to the consumer's callback carrying a transition (§1.5, Transition); no call at all when nothing did.

**Steps**:
1. [x] - `p1` - **WHEN** the consumer creates the observer, passing that domain's own registered-extensions source and that domain's own key, and registering its callback - `inst-when-create`
   1. [x] - `p1` - Validate the given domain key against the navigation substrate's own `domain-key` production — a single `name`, checked with the name-validity check (`cpt-frontx-algo-routing-navigation-substrate-name-validity`, Validity), so a key carrying `.` or any other character outside the `name` alphabet fails it — and validate every extension token the given registered-extensions source declares against the name-validity check alone (`cpt-frontx-algo-routing-navigation-substrate-name-validity`), here and on each later read — synchronously, before the resolution that uses them runs — and **THROW** a clear error naming the first offending value if any fails; only once this validation passes, read the current location, parse it via the grammar codec, resolve the entries carrying this domain key through the entry resolution primitive (`cpt-frontx-algo-routing-route-ownership-signal-entry-resolution`), and record the just-resolved ordered entry list as the observer's previously reported state - `inst-initial-resolve`
   2. [x] - `p1` - Subscribe to the navigation substrate's fan-out (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`) — **before** reporting the initial transition below, not after — so that a synchronous re-navigation the consumer's own first callback performs (step 1.3, below) is caught by this same subscription rather than missed entirely, exactly as any later navigation would be. Step 1.1's own baseline is already recorded by this point, so a reentrant dispatch this subscription catches during step 1.3 has a correct previously-reported state to diff against - `inst-subscribe-fanout`
   3. [x] - `p1` - Report an initial transition, carrying the cause `initial`, whose Entries are the just-resolved ordered list and whose diff reports every present extension token as `Added` (and as `Unresolved` too, for any entry paired with "unresolved") — **IF** this call throws, release the subscription registered in step 1.2 before propagating the throw: this step runs after that subscription already exists, so a throw here must not leave it registered with no release callback ever reaching the caller, since one is only returned by step 1.4 below, which a throw here prevents from being reached at all - `inst-initial-report`
   4. [x] - `p1` - **RETURN** the release callback (`cpt-frontx-algo-routing-route-ownership-signal-release`) to the consumer, closed over the subscription registered in step 1.2 - `inst-return-release`
2. [x] - `p1` - **WHEN** the navigation substrate's fan-out notifies the observer of a navigation, carrying the notification's navigation kind - `inst-when-navigation`
   1. [x] - `p1` - Read the current location, parse it via the grammar codec, and resolve the entries currently carrying this domain key through the entry resolution primitive, against the registered-extensions set read afresh for this resolution, validated as in step 1.1 - `inst-resolve-current`
   2. [x] - `p1` - Compute the diff between the newly resolved ordered list and the previously reported one: extension tokens present now but not before are `Added`; present before but not now are `Removed`; present in both with different ordered payload params are `Payload-changed`; whether the relative order of tokens present in both changed at all is `Reordered`; entries currently paired with "unresolved" are also listed under `Unresolved`, restating a subset of the just-resolved Entries rather than computing a further diff category - `inst-compute-diff`
   3. [x] - `p1` - **IF** every one of `Added`, `Removed`, `Payload-changed`, and `Reordered` is empty or false — regardless of whether the just-resolved Entries list itself is empty or non-empty - `inst-if-diff-empty`
      1. [x] - `p1` - Report no transition — nothing about this domain key's own entries changed; this is, in particular, what a navigation that changes only a foreign domain key's own entries, or the hash, produces, since resolution reads only the entries carrying this domain's own key. Record the newly resolved ordered entry list as the observer's new previously reported state, immediately — there is no consumer callback in this branch that could fail to finish processing it - `inst-no-report-unchanged`
   4. [x] - `p1` - **ELSE** - `inst-else-diff-nonempty`
      1. [x] - `p1` - Report a transition carrying the newly resolved Entries, the computed diff, and the cause — the navigation kind (`push`, `replace`, or `history`) of the history notification that triggered this run - `inst-report-transition`
      2. [x] - `p1` - Record the newly resolved ordered entry list as the observer's new previously reported state — **only once step 2.4.1's own report call returns without throwing**: a consumer callback that throws while processing a transition has not finished processing it, so the baseline must stay exactly where it was, at the previously reported state, rather than silently advancing past a transition the consumer never actually handled. The practical effect: the next navigation that returns to the identical resolved state recomputes the identical, non-empty diff against that same unmoved baseline and reports it again, instead of diffing against a state the throwing callback never actually saw take effect and finding nothing to report - `inst-record-navigation-state`

**Key-mismatch note**: A domain's own key is fixed at this observer's own creation and neither step 1 nor step 2 ever updates it in place. If no entry in the current location carries that key at all, steps 1.1 and 2.1 resolve an empty ordered list — not a fault condition, but the ordinary outcome for a domain key nothing currently addresses, reported (or diffed) exactly like any other resolution. A domain's key is its own declared route, declared once at that domain's registration (PRD §1.4, Glossary, domain key), so this algorithm has no mechanism, and no need for one, to replace the key of an observer still running.

**Re-entrancy note**: The observer holds no queue of its own. A navigation that a consumer's own `onTransition` callback issues from inside a transition it is receiving reaches the observer as a later round of the navigation substrate's fan-out, so the observer's runs of steps 2.1-2.4 never nest or interleave and each baseline commit (step 2.4.2) completes before the next run starts. Deferral, the bound on consecutive deferred rounds, and isolation of a throwing callback belong to the fan-out dispatcher (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`, step 4.4). The observer's initial report (step 1.3) runs outside any fan-out round, so a navigation its callback issues runs before that callback returns; step 1.2 subscribes before the initial report for that reason.

**Rationale**: Reporting the whole ordered entry list, not only what changed, is what lets a consumer render a domain's own current occupancy directly from one transition without reconstructing it from a sequence of diffs; carrying the diff alongside it is what lets that same consumer act only on what actually changed, at whatever occupant count the domain admits (`cpt-frontx-routing-fr-concurrent-occupant-projection`). Separating `Payload-changed` from `Added`/`Removed` is what keeps a domain from double-mounting an occupant whose parameters merely moved — the very case the URL grammar's own structural-reset rule treats as leaving every nested domain's own entries untouched (DESIGN §1.1, Structural reset) — and separating `Reordered` from both is what lets a domain that assigns meaning to entry order (a stack of sheets, a widget layout) react to a pure reorder without mistaking it for an occupancy change. Filtering out an empty diff is the one case this algorithm treats as not worth reporting: nothing about this domain's own occupancy, payload, or order could have changed when every diff category is empty. Reporting an initial transition at creation, rather than only from the first subsequent navigation, is what covers a cold load or a reload — the very case a consumer most needs this signal for — from the first moment the observer exists, even when that initial transition's own Entries list is empty.

### Observer Release

- [x] `p2` - **ID**: `cpt-frontx-algo-routing-route-ownership-signal-release`

**Input**: An observer created by `cpt-frontx-algo-routing-route-ownership-signal-observe-change`, at whichever domain it was created for, and the internal subscription it registered at creation: the navigation substrate's fan-out.

**Output**: The subscription this observer itself registered, unsubscribed; the observer reports no further transitions after this point, including a transition from a fan-out round already in progress at the moment release was called (Round-in-progress note, below) (Queued-round note, below: a round still queued when release is called skips the released observer).

**Steps**:
1. [x] - `p1` - **WHEN** the consumer calls the release callback returned at observer creation - `inst-when-release-called`
   1. [x] - `p1` - Unsubscribe from the navigation substrate's fan-out subscription registered at observer creation - `inst-unsubscribe-fanout`
   2. [x] - `p1` - **IF** the release callback is called again after the first call - `inst-if-called-again`
      1. [x] - `p1` - Treat the call as a no-op — nothing is subscribed to unsubscribe from a second time - `inst-release-repeat-noop`
2. [x] - `p1` - **RETURN** - `inst-return-release-done`

**Round-in-progress note**: The navigation substrate's own fan-out dispatch fixes a round's composition from a snapshot taken when the round starts, but always skips a callback no longer present in the live subscriber registry by the time the round's own iteration reaches its slot (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`) — a callback's own release always wins over a still-pending, not-yet-invoked slot a round's snapshot reserved for it. Calling this observer's own release function removes its callback from that live registry immediately (step 1.1), so if a fan-out round is already in progress at that moment and this observer's own callback is part of that round's snapshot but has not yet been invoked, that pending invocation is skipped, not delivered. An invocation of this observer's callback that already completed earlier in the same round, before release was called, is not undone.

**Queued-round note**: A fan-out round still queued when release is called skips the released observer through the dispatcher's liveness check.

**Rationale**: The signal holds no lifecycle notion of its own beyond the subscriptions its own observer registers (§4, No Feature-Owned State Machine), so leaking one is entirely this algorithm's own responsibility to prevent. Releasing the fan-out subscription this observer itself registered is what DESIGN §4 already names this feature as the owner of preventing, at whichever domain it was created for. Unsubscribing from the fan-out immediately, in step 1.1, rather than deferring it to some later point, is what makes the Round-in-progress note's guarantee hold: release only ever prevents an invocation still pending in a round already in progress, it never needs to retract one already delivered.

### URL Back-Projection Helper Via Own-Key Rewrite

- [x] `p2` - **ID**: `cpt-frontx-algo-routing-route-ownership-signal-url-back-projection`

**Input**: A domain key; a delta — an ordered list of entries (`{extension, params}`) to add; a list of extension tokens to remove; a list of `{extension, params}` pairs whose payload changed in place with the extension unchanged; a list of `{oldExtension, entry: {extension, params}}` pairs each replacing an existing entry's own extension token with a new entry at that same position; and, optionally, a new relative order for this domain's own currently-present entries, applied only within the positions those entries already occupy; and `clearedDomainKeys`, a list of the nested routed domains' keys whose entries leave in this same write (§1.5, URL back-projection — input); and the history verb the caller chooses, `push` or `replace` (§1.4, Binding obligation, point 6).

**Output**: One `push` or `replace` call, whichever verb the caller supplied, against the shared history, that mutates only this domain key's own entries and removes only the entries under the domain keys `clearedDomainKeys` names, leaving every other entry in the URL exactly as it was. The helper takes no hash; the codec copies the current hash unchanged (DESIGN §2.1, Control Boundary).

**Steps**:
1. [x] - `p1` - A caller calls this helper with the domain key, the delta and the chosen verb — the FrontX router, to write a runtime command for a domain, passing the command's verb, `push` or `replace`, or to write its own `replace` after a user's change to the URL (§1.4, Binding obligation, points 3, 6 and 9), or an occupant's own engine provider, to write that occupant's own entry's own parameters as a payload change (§1.1) - `inst-consumer-calls-helper`
   1. [x] - `p1` - Validate the given domain key, and every domain key the delta's `clearedDomainKeys` names, against the navigation substrate's own `domain-key` production — a single `name`, checked with the name-validity check (`cpt-frontx-algo-routing-navigation-substrate-name-validity`, Validity) — and validate every extension token named anywhere in the delta (its added list, its removed list, its payload-changed list, the old and new extension of every replaced pair, and its reordered list, when given) against the name-validity check alone — synchronously, before any parsing runs — and **THROW** a clear error naming the first offending value if any fails - `inst-validate-back-projection-tokens`
2. [x] - `p1` - Read the current location and parse it via the grammar codec (`cpt-frontx-algo-routing-navigation-substrate-grammar-parse`), preserving the full parsed entry list of every domain key, not only the given one - `inst-parse-current`
3. [x] - `p1` - Compose this domain key's own new ordered entry list, preserving position: keep every currently parsed entry under this domain key whose own extension is named by neither the delta's removed list nor, as an old extension, the delta's replaced list, in its existing position; apply the delta's payload-changed pairs to the matching entries in place, at their existing position, by replacing each matching entry's own parameter list wholesale with the pair's own `params` — never merging it with the parameter list that entry already carried; replace, at its existing position, each entry the delta's replaced list names by its old extension token with the delta's given new entry for that pair; **IF** the delta names a reorder for this domain, reassign the entries surviving the steps above to the identical set of positions they already occupy among this domain's own entries, in the given new relative order, touching no other domain's own entries; append the delta's added entries, in the order the caller supplied them, at the end - `inst-compose-own-entries`
   1. [x] - `p1` - **IF** the delta names a replacement whose `oldExtension` is carried by no entry currently under this domain key, **THROW** a clear error naming the domain key and that old extension token, writing nothing — neither this domain key's own rewrite nor the removal of any entry under the delta's `clearedDomainKeys`. A replacement stands its new entry at the old entry's *own position*, and an absent token has no position, so the operation the pair names cannot be performed at all; appending the new entry at the end of the full list instead would silently demote the pair to an addition and produce exactly the entry order `replaced` exists to stop producing. Checked before the reorder permutation check below, so a delta getting both wrong is refused on the cause the reorder's own surviving set is derived from. The error names the domain key and the missing token because that is what a consumer acts on: re-read the live entry list, recompute the delta against it, and call again naming the operation that list admits - `inst-replaced-old-extension-present-check`
   2. [x] - `p1` - **IF** the delta names a reorder, read each surviving entry by the extension token it carries in the *currently parsed* location, never by a token the same delta introduces: an entry the delta replaces is named by its `oldExtension`, since `reordered` orders positions and never also renames what stands in them, and an entry the delta adds is never named at all, since additions land after this step, at the end of the full list (step 5), outside the positions a reorder may touch. **IF** the given order is not exactly a permutation of that surviving set — a survivor missing from it, a token outside it, or a token named twice — **THROW** a clear error naming the domain key and the given order, writing nothing: a short order would silently drop a survivor the caller never asked to remove, and a repeated token would silently stand the identical entry at two positions, both of which reach the URL as a change the caller did not ask for and cannot see in its own delta - `inst-reordered-permutation-check`
4. [x] - `p1` - **FOR EACH** domain key the delta's `clearedDomainKeys` names - `inst-foreach-cleared-domain-key`
   1. [x] - `p1` - Remove every entry in the currently parsed entry list whose own `domainKey` equals that key — unless that key is this domain key itself, whose own entries step 3 alone governs — in the same history write as step 7: exactly the named key, never a key inferred from any key's shape, from a lexical prefix, or from the delta's removed or replaced tokens; a named key no entry carries removes nothing (structural reset, `cpt-frontx-routing-adr-domain-occupancy-addressing-granularity`) - `inst-clear-nested-domain-entries`
5. [x] - `p1` - Compose the full entry list to serialize, in one pass over the currently parsed full list rather than as a separate own-key block appended to a foreign-entries block: every currently parsed entry under this domain key that step 3 kept unchanged, applied a payload change to, replaced with a new entry, or reassigned within the reordered positions, retains its own absolute position in the full list, exactly where the currently parsed list already had it — a replaced entry's new extension token occupies the old entry's own position, and a reordered entry occupies whichever of this domain's own positions the given new order assigns it; every entry under every other domain key is copied verbatim at its own existing position, minus whatever step 4 removed; every entry the delta names as added is appended once, in the caller's own given order, at the very end of the full list, after every entry named above. This domain key's own entries are never regrouped into a single contiguous block — an own-key entry that was interleaved among foreign entries in the currently parsed list stays interleaved there in the composed list, at that same position - `inst-compose-full-list`
6. [x] - `p1` - Serialize the composed entry list, the current pathname, and the current hash via the grammar codec (`cpt-frontx-algo-routing-navigation-substrate-grammar-serialize`), copying the pathname and the hash unchanged from the parse of step 2; the helper takes no hash of its own (DESIGN §2.1, Control Boundary) - `inst-serialize`
7. [x] - `p1` - Call the shared history's `push` or `replace` — whichever verb the caller supplied in step 1, never a verb this helper fixes itself — with the serialized URL - `inst-call-history`
8. [x] - `p1` - **RETURN** - `inst-return-reflected`

**Collision note**: A delta may name an extension token this domain key already carries, or name one twice within itself — an `added` entry whose token an entry under this domain key already holds, an `added` list carrying one token twice, or a `replaced` pair whose new entry's token another entry under this domain key already holds. None of these is a position this helper can compose: two entries sharing one domain key and one extension token are not a URL this grammar can express, which is exactly why the codec refuses to serialize such a list (`cpt-frontx-algo-routing-navigation-substrate-grammar-serialize`, step 2.4). Step 6 therefore **THROWS** that same duplicate-extension error, naming the two colliding entries, and step 7 never runs — the location is left exactly as it was. Unlike the validation of step 1.1, this failure cannot be raised before the parse: whether an added token collides is a fact about the *current* URL, not about the delta alone. A caller reopening an entry under a token already present expresses it as a payload change, or as a removal and an addition in the one delta — the removal clears the token's own position first, so the addition at the end of the list collides with nothing.

**Single-write note**: Each call issues exactly one history write, and that one write both applies the delta to this domain key's own entries and removes the entries under exactly the domain keys `clearedDomainKeys` names; no part of a call — the clearing included — is ever issued as a write of its own, before or after. A call never touches a history entry other than the one its own verb writes — the new entry under `push`, the current one under `replace` — so the entry a `push` leaves behind keeps every entry it carried, the nested domains' entries included. This is the whole of this package's part in leaving a parent: it decides neither which keys to clear nor when to call. That a Back step afterward brings the host back together with its nested occupants' own entry parameters, and that the settle commands of the chains restoring them write nothing, is the FrontX router's behaviour built on this one write (§1.4, Binding obligation, point 8).

**No-op note**: This helper writes on every call. A delta naming no change at all — an empty delta, or one whose every named token is absent — still composes the current entry list and still issues exactly one `push` or `replace` of the result, so two consecutive empty deltas produce two identical history calls and, under `push`, two indistinguishable history entries. No comparison against the current URL suppresses the write, because a caller that wants a back step to return to the state it is leaving is entitled to ask for one. Deciding whether anything actually changed belongs to the caller, which already knows — §1.4's Binding obligation has the FrontX router call this helper to write a runtime command for a domain, or its own write after a user's change to the URL, only when the result differs from the live URL (§1.4, points 3 and 9). The same applies to a removed or payload-changed token this domain key does not currently carry, and to a `clearedDomainKeys` key no entry carries: that name matches no entry and changes nothing, and the call still writes. A `replaced` pair whose `oldExtension` this domain key does not currently carry is **NOT** among those tolerated cases and never reaches this note: unlike a removal, whose postcondition — that token absent — already holds, and unlike a payload change, which is inert with no entry to rewrite, a replacement has an effect of its own that an absent position makes impossible to deliver, so step 3.1 refuses it and writes nothing.

**Escape-canonicalization note**: "Verbatim", for every entry this delta does not name, means its structure — its domain key, its extension token, and its ordered parameter list, each preserving what it decoded to — not its original bytes. Step 2 parses the whole location and step 6 re-serializes it, so every entry in the URL, including every entry under another domain key, comes back in the codec's own canonical encoding: a percent escape covering a character the encoder does not escape is written out as that character (`?other=x;q=%41` returns as `?other=x;q=A`), while an escape the encoder does need keeps its escaped form (`;q=a%20b` returns unchanged). What survives byte for byte is the foreign *segment* — a query segment that never parsed as an entry of this grammar at all (an OAuth `code`, an analytics `utm_*`), which the codec carries through as raw text and re-emits after the entries. A consumer that needs a byte-exact value from another party's query must therefore keep it in a foreign segment, not in an entry under a domain key of this grammar.

**Timing note**: This helper's guarantee — that a call issued eagerly still lands on the browser's own current, post-move entry list — holds for a user's own back/forward step, and for a third-party history move that has already completed by the time this helper is called: in both cases the browser's own location has already settled to its post-move value before any of this library's own code runs, even though this library's own notification of that move still lags asynchronously behind it (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`). It does not hold for a `go` call issued through this same navigation-substrate instance: unlike a user's own gesture or an already-completed third-party move, this instance's own `go` call does not complete synchronously at its own call site — the browser processes the move, and raises the event this library's fan-out observes, only afterward. Calling this helper in the window between this instance's own `go` call and the fan-out's own notification of the move that call produced is therefore not a supported use. A caller that wants to write after issuing its own `go` call instead waits for the transition that call produces (§3, Observable Transition Signal) before calling this helper.

**Rationale**: Reading and re-serializing the full currently parsed entry list, rather than mutating a fragment of the raw URL string directly, is what lets this helper touch only the domain key it was asked to change plus the entries under the nested domain keys the caller named — every other domain key's own entries pass through step 5 unexamined and unchanged, satisfying the Control boundary (DESIGN §1.1) that keeps this helper from ever reading or editing another domain's own part of the URL beyond the FrontX router's own structural-reset write, which is no exception to the rule for shell, extension or host code. Taking the nested domain keys from the caller rather than deriving them is what the grammar itself requires: a domain key is the domain's own declared route, a single `name` carrying no ancestry, so nothing about a key's shape says which extension's zone it sits in — only the FrontX router's own orchestration knows which domains leave with a departing extension (DESIGN §2.3, O7). Clearing them in the same single write as the parent's own change, never in a write of their own, is what keeps the history entry being left intact: no write ever strips a nested domain's entries from that entry, so a Back step can return to the host together with its nested occupants' own parameters (§1.4, Binding obligation, point 8). A payload-only change or a pure reorder of a parent entry leaves every nested entry untouched, because the caller names no nested key for either — nothing about which extension occupies that entry changed (DESIGN §1.1, Structural reset). Giving `replaced` its own operation, rather than expressing a switch as a `removed` plus an `added`, is what keeps the new entry at the old entry's own position instead of at the end of the full list; `reordered` needs its own operation for the identical reason, since a domain's own entries taking a new relative order among themselves is not expressible as any combination of the other four without also implying an add, a remove, or a position at the end that was never asked for. Leaving the choice of `push` versus `replace` to the caller, rather than fixing one verb for every call, is what lets the same helper serve both an opening write — where a `push` lets a later back step undo exactly what was just opened — and a closing write — where a `replace` avoids resurrecting a dismissed entry on a later back step — without this algorithm needing two names for what is otherwise one identical composition (§1.4, Binding obligation, point 6).

The validity and equality checks are the navigation substrate's predicates, never a comparison of the router's own (DESIGN §2.3, O1, O3a, O3b).

## 4. States (CDSL)

### No Feature-Owned State Machine

Not applicable to the occupancy state machine, which is the runtime's. This feature holds no occupancy or binding lifecycle of its own to model as named states with guarded transitions — an observer's own lifecycle is only "subscribed" or "released" (§3, Observer Release), a lifetime, not an occupancy state machine, at any domain. Occupancy, cardinality, and any state machine tracking which route owner currently occupies a domain belong entirely to the runtime that executes the FrontX router's actions chains — the `mfes` runtime's own mount strategies and registry (`cpt-frontx-adr-extension-domain-occupancy`). Modeling that lifecycle here would duplicate a domain this package does not own and must stay agnostic of (`cpt-frontx-routing-principle-publishes-not-orchestrates`), so no state machine is defined for this feature. The FrontX router's kept initial route, deferred write and last-command record each have a lifecycle, specified in flow steps 7.1, 7.5, 8.1, 8.2 and 9 and in Binding obligation points 3, 9 and 10, with no named-state machine.

## 6. Acceptance Criteria

- [x] Given every entry currently carrying one domain key and that domain's own set of registered extensions, entry resolution names each entry's own matching route owner or reports it unresolved, using the navigation substrate's own name-equality predicate and never re-implementing it.
- [x] A consumer creates the observer per domain by passing that domain's own registered-extensions source as a plain argument, never through an injected port, together with the domain key it was handed.
- [x] On creation, the observer resolves and reports the current ordered entry list for its own domain key before any subsequent navigation occurs, so a cold load or reload is covered from the observer's first moment, not only from the first navigation after it — including when that initial list is empty.
- [x] An observer subscribes to the navigation substrate's fan-out *before* it reports its own initial transition: a consumer whose very first callback navigates synchronously — the deep-link → mount → redirect pattern — has that navigation's own resulting transition delivered exactly once, not lost.
- [x] A consumer callback (`onTransition`) that throws does not advance the observer's own baseline: the next navigation to the identical resolved state re-delivers the identical transition rather than silently producing an empty diff — and therefore no report at all — forever after. The throw is still isolated from every other subscriber sharing the same fan-out round, exactly as any other subscriber's own throw is.
- [x] A consumer callback that throws on the very first, initial report leaves zero live subscriptions on the navigation substrate's fan-out — the subscription registered ahead of that first report (step 1.2) is released before the throw propagates out of observer creation, so a caller that catches the throw and does nothing further is not left with a stale registration that keeps invoking that same callback on every later navigation.
- [x] On every subsequent navigation that changes something about a domain key's own entries, the observer reports exactly one transition carrying the full ordered entry list and a diff: extension tokens newly present are `Added`, extension tokens no longer present are `Removed`, an extension token present both before and after with different payload params is `Payload-changed`, a change to the relative order of persisting tokens is `Reordered`, and an entry whose own extension token matches no registration is listed under `Unresolved`, a restated subset of Entries rather than a further diff category.
- [x] No transition is reported when every one of `Added`, `Removed`, `Payload-changed`, and `Reordered` is empty, regardless of whether the current Entries list itself is empty or non-empty — including a navigation that changes only a foreign domain key's own entries or the hash, because resolution reads only the entries carrying this domain's own key.
- [x] The observer adds no queue of its own: a navigation its callback issues from every transition it receives is a later fan-out round, and a runaway loop of such navigations is stopped by the navigation substrate fan-out's bound on consecutive deferred rounds (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`, step 4.4; the substrate's own criterion on a listener that navigates from every round it receives).
- [ ] A payload-only change to an entry is reported as `Payload-changed` alone, never as `Added`/`Removed`; the FrontX router names no domain key to clear for it, so no nested domain's entries leave with it.
- [x] Creating an observer returns a release function; calling it unsubscribes the observer from the navigation substrate's fan-out, and the observer reports no further transitions afterward — including skipping a still-pending, not-yet-invoked delivery from a fan-out round already in progress at the moment release was called, without undoing one the round already delivered earlier. Calling it again is a no-op.
- [x] More than one observer may exist in the same realm at once — one per domain a consumer holds, regardless of how many concurrent occupants that domain admits — each independent, each with its own registered-extensions source and its own domain key, each released independently.
- [ ] Resolving a URL several domains deep is a wave of independent per-domain resolutions, not one event: a deeper domain's own observer exists and reports only once the runtime has mounted the route owner whose zone contains it and the FrontX router has created that deeper domain's own observer, this feature publishes no signal asserting that an address resolved end to end, and a domain several steps deeper reporting nothing yet is indistinguishable, at any shallower domain, from that deeper domain's own wave simply not having arrived.
- [x] The back-projection helper issues exactly one `push` or `replace` call, whichever verb the caller supplied, that writes the given domain key's own delta, removes the entries under exactly the domain keys `clearedDomainKeys` names, and leaves every entry under every other domain key, and every entry under this domain key the delta does not name, exactly as it was.
- [x] `clearedDomainKeys` is applied exactly as given, never inferred: from `/en?screen=tenants;tenantId=ABC&tabs=contacts&legend=right&modal=create-contact`, a call for the `screen` domain naming `[tabs]` removes `tabs=contacts` and keeps `legend=right` and `modal=create-contact`, because only `tabs` was named; a named key no entry carries removes nothing, and the call still issues its one write; a named key that is not a valid `name` throws `invalid-domain-key` before anything is written; and a call naming no domain key to clear removes no entry outside the calling domain key's own delta, whichever tokens that delta removes or replaces.
- [ ] The back-projection helper takes no hash: its single write carries the URL's current hash unchanged, as the codec copies it (DESIGN §2.1, Control Boundary).
- [x] A `reordered` list that is not exactly a permutation of the domain's own surviving entries — one short, one too many, or naming a token twice — throws before anything is written, and the location is unchanged. The survivors it must name are the tokens the *current* location carries, so a delta that both replaces `a` with `c` and reorders names `a`, not `c`, and a delta that both adds `c` and reorders never names `c` at all.
- [x] A `replaced` pair whose `oldExtension` no entry under that domain key currently carries throws before anything is written, and the location is unchanged — the entries under the delta's `clearedDomainKeys` included, since nothing is written for a replacement that never happened. This is not one of the absent-token cases the No-op note tolerates: a caller opening an entry at a position that does not yet exist expresses it as an addition instead.
- [x] A delta whose `added` list names an extension token already present under that domain key, or names one token twice, throws the codec's own duplicate-extension error and writes nothing — as does a `replaced` pair whose new token another entry under that domain key already holds. Reopening an entry under a token already present is expressed instead as a payload change, or as that token's removal and addition in the one delta.
- [ ] Every call writes: an empty delta, or one naming only tokens the domain key does not carry, still issues exactly one `push` or `replace` of the composed list, so two consecutive empty deltas produce two identical history calls. Deciding whether anything changed is the consumer's, under §1.4's Binding obligation.
- [x] An entry under another domain key survives a write with its structure intact but in the codec's own canonical encoding, not byte for byte: `?other=x;q=%41&mine=a` comes back as `?other=x;q=A&mine=a`, while `;q=a%20b` keeps its escape. A query segment that never parsed as an entry at all — an OAuth `code`, an analytics `utm_*` — is the value that survives byte for byte.
- [ ] The FrontX router passes the helper the verb of the command it writes — the application request's own `push` or `replace` for a command the runtime issues when the domain accepts the request, and `replace` for a command issued when a request settles — and `replace` for its own write after a user's change to the URL; so an opening request carrying `push` lets a back step close what was opened, a closing request carrying `replace` keeps a back step afterward from reopening it, and a URL-driven chain carrying `none`, which issues no command at acceptance, never creates a history entry.
- [ ] The transition the back-projection helper's own history call produces carries the cause `push` or `replace`, so the FrontX router dispatches nothing for it; the same holds for any transition whose cause is `push` or `replace`.
- [ ] Right after dispatching the chains of a page load's first `initial` transition, the FrontX router clears every entry from the URL with `replace`, as flow step 8 states, and the URL then carries only the entries the runtime's commands write: `?screen=profile&sidebar=hello-world`, with `profile` mounting and no sidebar extension domain implemented, ends after the load as `?screen=profile`; a URL `?screen=reports` with `reports` unregistered and the screen domain ready mounts nothing and loses the entry once the load finishes. After dispatching for a back or forward step, the FrontX router writes the domain's entries with `replace`, as flow step 8 states: entries that do not resolve are dropped, and a domain that does not declare `unmount_ext` whose entries the change left empty gets the extensions of the last command it received for it written back; in a screen domain that declares no `unmount_ext`, Back to an address without a screen entry sends the screen domain no chain, leaves the screen showing, and writes the screen's last commanded extension back into the URL.
- [ ] The FrontX router clears the URL after a page load's first `initial` transition even when sending one of that transition's chains throws: the throw leaves no entry of the initial route in the URL, and no later `initial` transition clears.
- [ ] An entry that does not resolve is logged only for a transition after the domain's first: the URL a domain's observer finds when it starts — a page load's initial route included — logs nothing for an unresolved entry, and a later back or forward step that brings an unresolved entry logs it.
- [ ] A page load keeps its initial route for that load: at `/en?screen=tenants;tenantId=ABC&tabs=contacts`, the `tabs` domain, whose observer starts once `tenants` has mounted and so reads the cleared URL, takes its first resolution from the initial route, so the FrontX router sends the `mount_ext` of `contacts`; and the settle commands for `tenants` and `contacts` write each entry with its parameters as the initial route carried them, so the URL ends as `/en?screen=tenants;tenantId=ABC&tabs=contacts`. The FrontX router discards the initial route at the first command carrying `push` or the next back or forward step, whichever comes first: a nested domain whose observer starts after that resolves against the live URL, and a later write of an extension the initial route named carries no parameters from it.
- [ ] The FrontX router rejects, by throwing at registration, a routed domain whose route is not a valid `name` — `screen.tabs` among them — and one whose route another routed domain live in the page holds; the rejected domain is never partly admitted, and once the domain holding that route is released, its route is free.
- [ ] The FrontX router rejects, by throwing at registration, an extension of an admitted domain whose route does not reduce to a valid `name` once one leading `/` is stripped, and one whose name another extension of that domain holds; it ignores an extension of a domain it did not admit as routed, and `assignOccupantValue` returns `undefined` for a domain or an extension it did not admit.
- [ ] `connect` is called once, before any domain or extension registers, and the FrontX router uses the executor and the type system it receives only to send the chains of a page load or a back or forward step.
- [ ] `assignOccupantValue` returns `{ domainKey, extension }`, the domain's route and the extension's name, for an admitted extension of an admitted domain; `startDomain` starts the domain's observer once its root has attached, and a second call reuses it; `stopDomain` stops it before the domain detaches and drops the domain's last-command record and any deferred write; and `ownEntryAddress()` returns the runtime's own occupant value once validated in a routed extension's runtime, returns `undefined` in the shell runtime, whose router was never supplied navigation, and throws in an extension runtime whose router was supplied navigation without an occupant value.
- [ ] A domain registered before the runtime's navigation is supplied is still cleared when its host extension is dropped: supplying navigation records every already admitted domain under the runtime's occupant value, and removes its record under a previous occupant value, so the enclosing router's write that drops the host clears that domain's entries too; with no occupant value nothing is recorded.
- [ ] A runtime whose FrontX router was supplied navigation but has no occupant value — an extension with no route of its own or of its domain, or a failed occupant-value exchange — is not the shell runtime: it has no access to the router, so `ownEntryAddress()` throws in it and the engine-provider package's extension router and navigation facade refuse in it; only a runtime whose router was never supplied navigation is the shell runtime, where `ownEntryAddress()` returns `undefined`, and in a routed extension's runtime `ownEntryAddress()` returns its occupant value.
- [ ] The observer reads the domain's registered extensions at each resolution: an extension registered after its domain started is resolvable from the next navigation, so a back or forward step to its entry mounts it, and a released extension resolves as unresolved; the observer neither watches the registered extensions nor re-resolves entries when they change. A deep link stays lost only for an extension whose registration is not in place when its domain's observer takes its first resolution: the URL's entries are cleared after the page load's first transition, and the initial route stays captured only until the first `push` command or back/forward step.
- [ ] For a transition whose cause is `initial` or `history`, the FrontX router sends one `unmount_ext` per token that left the entries, only to a domain that declares `unmount_ext`, and one `mount_ext` per token that arrived and resolves, each its own actions chain carrying the history intent `none` and no `fallback`, removals dispatched before additions, without reading what is mounted; a removal that fails holds back no addition, and the domain's handler decides the outcome of every request. In an Optional or Concurrent domain, a Back step that removes an entry sends one `unmount_ext` for its extension, and the mounts lose that occupant.
- [ ] `unmount_ext` reaches only a domain that declares it: a Back step that removes the only entry of a domain declaring no `unmount_ext` sends that domain no chain at all, and a Back step that swaps that domain's entry for another sends only the `mount_ext` of the arriving extension.
- [ ] The FrontX router writes each runtime command for a domain through one back-projection call with the command's verb, showing exactly the extensions the command names, and reads neither the action type, nor the action's outcome, nor any strategy or cardinality of the domain.
- [ ] A command is written at acceptance, before the mount finishes: from `/en?screen=dashboard`, an application `mount_ext` of `settings` carrying the history intent `push` is accepted by the screen domain, the runtime commands the screen domain to show `settings` with `push`, and the FrontX router writes `/en?screen=settings` as one new history entry while the `settings` mount is still running.
- [ ] A command whose result equals the live URL writes nothing: when that `settings` request settles, the runtime commands the screen domain to show `settings` with `replace`, which equals the URL, so the FrontX router makes no back-projection call and no history call is made.
- [ ] Entries a command keeps keep their position and their parameters, a dropped extension with nothing named in its place is removed, and a newly named extension with nothing dropped is added at the end: from `/en?sheet=tenant-details;tenantId=456&sheet=user-contacts;contactId=123;view=active&widgets=pie;metric=revenue`, a command for the `sheet` domain naming only `tenant-details`, with `replace`, writes `/en?sheet=tenant-details;tenantId=456&widgets=pie;metric=revenue`; a later command for the `sheet` domain naming `tenant-details` and `user-contacts`, with `push`, writes `/en?sheet=tenant-details;tenantId=456&widgets=pie;metric=revenue&sheet=user-contacts` — `tenant-details` keeping `tenantId=456` at its position, and `user-contacts` appended after every entry. A command that drops exactly one extension of a domain and names exactly one new one writes the new one in the dropped one's position as `replaced`; a command that drops or names more than one removes the dropped extensions and appends the new ones.
- [ ] A command for a domain whose enclosing entry is absent from the URL is deferred: nothing is written for it while that entry is absent, and it is issued once that entry is present; the enclosing entry of a nested domain is the URL entry of the extension that hosts that domain.
- [ ] Two commands for the same domain that arrive while its enclosing entry is absent leave a single deferred write: the later command takes the place of the pending one; the write's verb is `replace` if either command carried `replace` and otherwise `push`; it is composed and compared against the live URL when the enclosing entry becomes present, and an equal result writes nothing; a back or forward step by the user before that entry is present cancels the deferred write before any observer dispatches for that step (the step's own write-back uses `replace`, and when it defers too, it is the write applied once the entry arrives), and an extension released while the write is deferred is dropped from it.
- [ ] The last-command record of a domain is replaced by each command and is kept even when the domain has no live observer; an extension is removed from it, and from any deferred write, when that extension is released; and it is dropped, together with any deferred write, when the domain stops.
- [ ] A Back step to an address whose screen entry names an unregistered extension leaves the current screen showing: the unresolved entry is dropped, the screen domain is then empty and declares no `unmount_ext`, so the last commanded screen is written back with `replace`.
- [ ] A command for a domain without a live observer writes nothing: once a domain's observer is released, a command the runtime issues for that domain makes no back-projection call and changes no entry in the URL.
- [ ] Dropping a host clears every domain nested beneath it, transitively. At `/en?screen=tenants;tenantId=ABC&tabs=contacts&notes=list&modal=create-contact`, the `tenants` extension's own runtime registered the `tabs` domain, so its FrontX router recorded `tabs` under the occupant value `{ domainKey: screen, extension: tenants }`; the `contacts` extension's own runtime registered the `notes` domain, so its FrontX router recorded `notes` under `{ domainKey: tabs, extension: contacts }`. A command for the screen domain naming `settings`, with `push`, is written as one back-projection call whose `clearedDomainKeys` names `tabs` and `notes`, and the URL becomes `/en?screen=settings&modal=create-contact`. Once the `notes` domain is released, the record holds no `notes` key under `{ domainKey: tabs, extension: contacts }`, and a later command that drops `tenants` names `tabs` alone.
- [ ] The signal, the entry-resolution primitive, the observer and the back-projection helper hold no registry of route owners (§1.4, Boundary note); nothing in this feature executes a mount or unmount itself, at any domain, or defines an occupancy state machine; the FrontX router dispatches a user's change to the URL and writes the runtime's commands, per the Binding obligation (§1.4), recursively at every routed domain, on top of the primitive, the signal, and the helper this feature publishes, reaching every mount and unmount only through `mount_ext` and `unmount_ext` actions chains.
- [ ] A domain's occupancy cardinality — how many route owners a domain may hold simultaneously, and how a race between two mounts resolves — is decided entirely by the runtime that executes the FrontX router's actions chains; this feature carries no notion of exclusive versus concurrent occupancy, and resolves no mount race of its own, at any domain. Of a domain's declaration the FrontX router reads one fact, whether it declares `unmount_ext`.
- [x] A domain key with no observer currently reading it is inert, not an error and not a fallback state; it is resolved correctly the moment a domain that reads it comes to exist, because every observer reads the URL's current, live state rather than a value captured earlier; the FrontX router's substitution of the initial route for a domain that starts during a page load is separate from the observer (§1.4, Binding obligation, point 9).
- [ ] Teardown of the occupant whose zone contains a nested routed domain — part of the parent action's own execution — releases that nested domain's observer through the FrontX router, so no observer keeps resolving and reporting against a domain key or a registered-extensions source whose owning zone no longer exists.
- [x] Observer creation and the back-projection helper each throw `invalid-domain-key`, synchronously and before anything is resolved or written, for a domain key that is not a single valid `name` — `screen.tenants.tabs` among them.
- [x] The console layout worked example resolves and back-projects exactly as pictured:

     &tabs=contacts

  `tabs` is the route the `tenants` extension's own zone declares for its nested tabs domain, carrying no reference to `screen` or to `tenants`, because a domain key never restates an ancestor; `modal` is the console's own root domain. The `screen`, `tabs`, and `modal` domains' own observers each resolve the one entry under their own key. An implementation **MUST** reproduce this example as one of its own acceptance scenarios.

- [x] The structural reset worked example resolves exactly as pictured, in both directions:

  ```
  before: /en?screen=tenants;tenantId=ABC&tabs=contacts&modal=create-contact
  after:  /en?screen=settings&modal=create-contact
  ```

  Given the delta for the `screen` domain — `{oldExtension: tenants, entry: {extension: settings, params: []}}` in the replaced list, so the screen entry's extension token goes from `tenants` to `settings` at the same position, and `[tabs]` in `clearedDomainKeys` — and the verb `push`, one call of the back-projection helper writes the after-URL above in one history write: it swaps `screen=tenants;tenantId=ABC` for `screen=settings` at that same position and removes `tabs=contacts`, while `modal=create-contact` is untouched, because `modal` is not among the named keys. Had the call named no key to clear, `tabs=contacts` would have survived as a stranded entry. An implementation **MUST** reproduce this example as one of its own acceptance scenarios.

- [ ] Leaving the `tenants` screen in the structural reset worked example above never rewrites the entry the user left: after the `push` write, the history entry before it still reads `/en?screen=tenants;tenantId=ABC&tabs=contacts&modal=create-contact`, with the nested `tabs` occupant's own entry intact. A Back step lands on it, a `history` transition, and the FrontX router turns the reported transitions into actions chains carrying the history intent `none` — the `mount_ext` of `tenants`, then, once the `tabs` domain's observer starts, the `mount_ext` of `contacts`, and an `unmount_ext` of `settings` only if the screen domain declares `unmount_ext` — bringing the `tenants` screen back together with its nested `contacts` tab, each reading its own entry's own parameters — `tenantId=ABC` included — and their settle commands equal the URL, so no back-projection call is made for them; a Forward step afterward returns to `/en?screen=settings&modal=create-contact` the same way, again creating no history entry.

- [x] Nesting inside a domain holding several occupants resolves exactly as pictured:

     &legend=right
     &widgets=line-b;range=30d
